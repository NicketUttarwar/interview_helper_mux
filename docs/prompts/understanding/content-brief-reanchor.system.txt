Re-anchor the existing content brief to the segmented timeline (see task in volley).

Patch the on-disk brief — do **not** rewrite `thesis` or topic names from scratch unless correcting a clear error.

Gap-fill: when `gap_fill_context.existing` is set, patch only fields listed in `gaps`; omit keys in `skip_fields`.

Goals:
- Assign `topics[].segment_ids` from manifest `topic_tags` and segment text.
- Enrich `key_claims[]`: `segment_ids`, `evidence_segment_ids`, `claim_type`, `depends_on_claim_ids` (preserve existing `id`s).
- Produce `topic_relationships[]` linking brief topics with evidence.
- Confirm or reject open hypotheses from pass 1 via `hypotheses_append` (`status`: `confirmed` | `rejected`).

Rules:
- Use only `segment_id`s present in input manifest/boundaries.
- Every `topic_relationships[]` entry needs at least one `evidence_segment_id` when possible.
- `depends_on_claim_ids` must reference `key_claims[].id` values from the brief.
- For shard/collate runs, union segment_ids and relationships across shards; dedupe relationships by (`from_topic`, `to_topic`, `relation`). Preserve cross-shard `depends_on_claim_ids`.
- If a hypothesis lacks segment evidence after reanchor, set `status: rejected` with a one-line reason in `statement` suffix or `reasoning_summary`.

Do not:
- Invent segment_ids not in input.
- Drop existing claims or topics unless contradicted by segment evidence.

Memory sync:
- `themes_append`: update `segment_ids` for matched themes (`sources: ["content_brief_reanchor"]`)
- `hypotheses_append`: confirm/reject open hypotheses from profile
- `style_patch` (optional): refine `pacing`, `tone`, or `interviewer_style` / `interviewee_style` only when segment mix clearly supports it — do **not** change `tone_class` or `format_class` unless segment evidence contradicts them
- `confidence_patch.content`: 0–1 for re-anchor quality

Investigations: `theme_unmapped` when a brief topic still has zero segments after reanchor.

Allowed `key_claims[].claim_type` values: `fact`, `opinion`, `prediction`, `anecdote`, `definition`.

## topic_relationships — graph discipline

Produce `topic_relationships[]` only here (not in pass 1). Each edge must be **evidence-backed**:

| relation | Meaning | Example |
|----------|---------|---------|
| `prerequisite` | Topic B requires understanding A | Product architecture before scaling story |
| `supports` | B reinforces or evidences A | Customer anecdote supports market thesis |
| `contradicts` | Tension or disagreement between topics | Bootstrapped vs VC path |
| `example_of` | B is a concrete instance of A | Single deployment story under "platform" topic |
| `returns_to` | Later segment callbacks earlier theme | Closing returns to opening thesis |

Rules:
- At least one `evidence_segment_id` per edge when manifest supports it.
- `from_topic` and `to_topic` must match existing `topics[].name` strings exactly.
- Avoid redundant A↔B pairs; pick the direction that matches narrative causality.
- Panel interviews: `returns_to` often links guest-specific threads back to shared theme — cite the callback segment, not the intro alone.

## Shard dedupe (re-anchor)

- Union `topics[].segment_ids` across shards; dedupe sorted unique ids.
- **Relationships:** Dedupe by (`from_topic`, `to_topic`, `relation`); merge `evidence_segment_ids` and `description` into the stronger entry (more segment evidence).
- **Claims:** Preserve all `id`s; union `segment_ids` and `evidence_segment_ids`; never drop cross-shard `depends_on_claim_ids`.
- **Hypotheses:** Confirm/reject with segment citations; rejected hypotheses need one-line reason in `reasoning_summary`.
- When the same claim appears in multiple shards with different types, prefer the type supported by the cited answer segment text.

## Quality bar

- Zero invented `segment_id`s.
- Every brief topic either has `segment_ids` or triggers `theme_unmapped` investigation.
- `confidence_patch.content` ≥ 0.7 only when topics, claims, and relationships are majority grounded; lower when flagged transcript regions dominate.
